# Двухступенчатый учёт времени: локальные часы + серверный леджер

Схема того, как визит считает время, когда связи нет, и как это потом сверяется с
сервером. Документ — карта, а не задача: пункты для исполнения нарезаются отдельно.

Опорные правила, которые уже действуют в коде: `F3.7` (клиент сообщает *elapsed*,
клуб считает деньги), `F6.3` (один интервал в приложении только *перечитывает* часы,
никогда не вычитает).

---

## 1. Общая картина: две ступени, две разные роли

```
┌─────────────────────────── КИОСК (клиент) ────────────────────────────┐
│                                                                       │
│   СТУПЕНЬ 1 — ЛОКАЛЬНЫЕ ЧАСЫ (правда для глаз игрока)                 │
│   ─────────────────────────────────────────────────                   │
│   Показывают остаток. Работают всегда, сеть не нужна.                 │
│                                                                       │
│      анкоры ──derive()──► 01:23:51 на экране                          │
│      (expiresAt, serverTime, runningSince, bankedSeconds)              │
│                                                                       │
│   Свойство: НЕ вычитает, а ПЕРЕИСЧИСЛЯЕТ из анкоров каждую секунду.   │
│   Поэтому пропущенные тики, сон машины и офлайн ничего не ломают.      │
│                                                                       │
│                              │                                        │
│                              │  unreportedSeconds()                   │
│                              │  «сколько клуб ещё не слышал»          │
│                              ▼                                        │
│   СТУПЕНЬ 2 — ОТЧЁТ (правда для денег)                                │
│   ────────────────────────────────                                    │
│   Раз в ~10 с отправляет ПОКАЗАНИЕ (не дельту!) серверу.              │
│   Офлайн — просто копит показание. Никакой очереди.                    │
└───────────────────────────────┬───────────────────────────────────────┘
                                │  session.heartbeat
                                ▼
┌────────────────────────────── СЕРВЕР ─────────────────────────────────┐
│   ЛЕДЖЕР — единственный источник истины о списании                     │
│   secondsUsed = max(secondsUsed, показание)   ← идемпотентно           │
│   Ответ: свежий SessionSnapshot → applySnapshot() → новые анкоры        │
└───────────────────────────────────────────────────────────────────────┘
```

Разделение ролей — суть замысла:

| | Ступень 1 (локальные часы) | Ступень 2 (серверный леджер) |
|---|---|---|
| Отвечает на вопрос | «сколько осталось» | «сколько списать» |
| Кто владеет | клиент | сервер |
| Нужна сеть | нет | да |
| Ошибка стоит | неверная цифра на экране | потерянные или двойные деньги |

## 2. Ступень 1 уже правильная — её не переписываем

`lib/store/slices/session.ts` → `derive()` уже переисчисляет из анкоров:

```
prepaid:   осталось = (expiresAt − serverTime) − (сколько держим снапшот)
postpaid:  накоплено = bankedSeconds + secondsSince(runningSince)
```

Почему это и есть корректный офлайн: часы **не зависят от того, тикало ли что-то**.
Их значение — функция от анкоров и текущего момента. Пропало 8 минут связи и 480
тиков — неважно, следующий же тик даст верную цифру.

```
   было бы counter-- (НЕПРАВИЛЬНО)        derive() (КАК СЕЙЧАС)
   ──────────────────────────────         ──────────────────────
   tick tick ░░░░░░░░ tick tick           tick tick ░░░░░░░░ tick
             ↑ офлайн, тиков нет                    ↑ офлайн
   → часы отстали на 8 минут              → часы верны сразу же
     дрейф навсегда остался в цифре         анкор не менялся
```

Отдельно уже решён перевод системных часов: `remainingSeconds()` в `lib/time.ts`
корректирует skew через `serverTime`, поэтому киоск с неверным временем показывает
ровно то, что продано.

## 3. Что происходит в офлайне: таймлайн визита (prepaid)

```
время →  0        10       20   ✂ ОБРЫВ ✂            8 мин            ✓ СВЯЗЬ
         │        │        │                                            │
экран    02:00:00 01:59:50 01:59:40 ... идёт, не мигает ... 01:51:40    01:51:40
         └── часы живы всю дорогу: анкор не менялся, derive() считает ──┘

отчёт    ✓        ✓        ✓        ✗    ✗    ✗    ✗    ✗              ✓
         послан   послан   послан   не ушёл (сеть)                      ушёл

показание  10       20       30      40 → 50 → ... → 510              520
           └── одно накопительное число, растёт монотонно ─────────────┘

сервер   used=10  used=20  used=30  ── used=30, не знает ──►          used=520
                                                            max(30, 520) = 520
```

Три вывода из картинки:

1. **Экран ни секунды не врёт** — офлайн для ступени 1 вообще не событие.
2. **Отчёт не теряется** — потому что это не 48 потерянных дельт по 10 с, а одно
   число, которое просто дорастает до 520.
3. **Догоняющего пересчёта не нужно** — сервер берёт `max` и мгновенно приходит к
   правде за один запрос.

---

## 4. Почему показание, а не дельта — главное решение

Отчёт дельтой (`+10 с`) требует, чтобы каждая дельта дошла **ровно один раз**.
Отчёт показанием (`всего 520 с от анкора`) не требует вообще ничего.

```
      ДЕЛЬТА (+= на сервере)                  ПОКАЗАНИЕ (max на сервере)
      ──────────────────────                  ──────────────────────────
  клиент  ──── +10 ────►  сервер          клиент ──── =520 ───►  сервер
                          used += 10                             used=max(...,520)
          ◄╳╳ ответ потерян                      ◄╳╳ ответ потерян
  ретрай  ──── +10 ────►                  ретрай ──── =520 ───►
                          used += 10                             used=max(520,520)
                          ═══════════                            ═══════════
                          СПИСАНО ДВАЖДЫ                         СПИСАНО ВЕРНО
```

Из «показание + max» бесплатно следуют три свойства:

- **идемпотентность** — повтор безопасен, значит ретраить можно сколько угодно;
- **устойчивость к переупорядочиванию** — пришло `520`, потом отставшее `480`?
  `max` игнорирует старое;
- **очередь не нужна** — состояние синхронизации это одно число, а не журнал
  операций. Отсюда и «офлайн-очереди» в проекте нет by design.

Показание всегда привязано к анкору, иначе после продления времени сервер сравнит
несравнимое:

```
report = { anchorId, elapsedSinceAnchor }

сервер:  if (anchorId === текущий_анкор)
             used = max(used, baseAtAnchor + elapsedSinceAnchor)
         else
             игнор  // показание от прошлой эпохи, клиент уже получит новый снапшот
```

## 6. Ассиметрия prepaid / postpaid — офлайн-лимит нужен только одному

```
PREPAID — безопасен сам по себе                POSTPAID — нужен предел
────────────────────────────────               ───────────────────────
expiresAt это СТЕНА, локальная:                долг растёт, стены нет:
                                               
 02:00 ──────────────► 00:00 СТОП               0 ──────────────────► ∞
       офлайн ничего не меняет                     офлайн = слепой рост
                                               
Игрок не может «доиграть лишнего»:             8 часов офлайна = счёт,
время кончится по локальным часам,             который игрок увидит
даже если сервер молчит.                       впервые уже огромным.
                                               
→ офлайн-лимит НЕ нужен                        → нужен потолок офлайна:
                                                 дальше него клуб решает
                                                 (пауза / вызов админа)
```

Правило, которым закрывается разница: **недоотчёт — безопасное направление**
(клуб не выставил счёт), **переотчёт — опасное** (игрок заплатил за то, чего не
играл). Поэтому `unreportedSeconds()` уже везде флорится в нуль, а на паузе
возвращает `0` — стоящие часы не жгут ничего.

## 7. Момент восстановления связи

```
offline ──────────────────────► online   (ребро true → false)
                                  │
                  ┌───────────────┼───────────────┐
                  ▼               ▼               ▼
        mutate(() => true)   отчёт-показание   один тост
        всё SWR обновить     догоняет леджер   «Связь восстановлена»
                                  │
                                  ▼
                          свежий SessionSnapshot
                                  │
                                  ▼
                          applySnapshot()  ← единственная дверь
                                  │
                                  ▼
                          новые анкоры → derive() → экран
```

Здесь работает то, что уже сделано в `components/realtime/realtime-provider.tsx`
(`useReconnectResync`): ресинк ходит через `applySnapshot()`, и **именно потому что
часы производные, принятие свежего дедлайна не может дёрнуть цифру** — это
перечитывание того же момента с исправленным skew. Игрок, смотревший на таймер весь
обрыв, видит продолжение, а не прыжок.

## 9. Границы (Non-goals)

- **Оффлайн-открытие визита** — не делаем. Вход без сервера требует нативного агента
  с локальной БД; на входе решение противоположное — вход запрещён (`OFFLINE_ENTRY_BLOCKED`).
- **Очередь отложенных операций** — не строим, см. §4: синхронизация это одно число.
- **Локальный биллинг** — сервер остаётся единственным, кто считает деньги (`F3.7`).

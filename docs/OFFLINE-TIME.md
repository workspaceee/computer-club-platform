# OFFLINE-TIME — двухступенчатый учёт времени и сверка с сервером

> **Что это.** Архитектурный документ одной темы: как клуб считает время, когда связи нет,
> и как этот счёт сходится с сервером, когда связь вернулась.
>
> **Зачем отдельным файлом.** `C2.13` закрывает *дверь* при обрыве (вход и деньги), но
> ничего не говорит про **уже идущий визит** — а это единственное место, где офлайн стоит
> денег. Тема пересекает стор, транспорт, агента и контракт API, поэтому она не влезает
> в один подпункт: из этого файла выводится семейство подпунктов (§12).
>
> **Статус.** Проект решения. Кода по нему ещё нет, кроме фундамента из §2.

---

## 0. Проблема

Сейчас в продукте **одна** ступень учёта — локальная. Она хорошая (см. §2), но у неё нет
второй половины:

1. **Периодического отчёта серверу нет вообще.** `heartbeat()` в `lib/mock/api/session.ts`
   написан, но его никто не вызывает по таймеру. Единственный вызов — `lib/seat.ts:160`,
   в `holdSeat()`, при постановке на паузу.
2. **Этот единственный отчёт при обрыве теряется молча.** Там стоит
   `heartbeat(usedSeconds).catch(() => {})`. Офлайн отчёт не доходит, ошибка съедается,
   локально время забанкано, а строка сессии на сервере считает, что не сыграно ничего.
3. **`heartbeat` неидемпотентен.** Внутри `session.secondsUsed += burn`. Ответ, потерянный
   в сети (запрос дошёл, ответ — нет), при повторе спишет те же секунды **второй раз**.
   Любая сверка после офлайна — это цепочка ретраев, то есть двойное списание по построению.
4. **Локальные анкоры не переживают перезагрузку.** Стор в памяти. Ребут станции в офлайне
   → анкоры потеряны, `fetchCurrentSession()` недоступен → клиент не знает ни остатка, ни
   дедлайна.

Итог: офлайн у нас сейчас *не считает неправильно* — он **не считает вообще на стороне клуба**.
Игрок играет, локальные часы честно тикают, сервер об этом не узнает никогда.

## 1. Две ступени: определения

| | Ступень 1 — **локальные часы** | Ступень 2 — **серверный леджер** |
|---|---|---|
| Где | `lib/store/slices/session.ts` + агент | строка `sessions` на сервере |
| Отвечает на | «сколько показать игроку **сейчас**» | «сколько клуб **списал**» |
| Единица | производная из анкоров, секунды | `secondsUsed` / `debtSeconds`, деньги |
| Живёт офлайн | **да**, бесконечно | нет |
| Авторитет | **нет.** Кэш и UX | **да.** Единственная правда о деньгах |
| При конфликте | всегда уступает | всегда выигрывает |

**Правило разделения (не нарушать):** ступень 1 никогда не является основанием списать
деньги, ступень 2 никогда не рисуется напрямую в HUD (её значение сначала становится
анкором ступени 1). Всё, что клиент имеет право сказать о времени — **сколько прошло**;
что это значит в деньгах, решает сервер (`F3.7`).

Ступень 1 существует не «на всякий случай», а потому что **матч нельзя прерывать из-за
сети**. Ступень 2 существует потому что **локальному счётчику нельзя верить про деньги**.
Обе нужны, и ни одна не является резервной копией другой.

## 2. Что уже сделано правильно и переписывать НЕ надо

Фундамент ступени 1 уже ggLeap-уровня, и это главная причина, почему задача выполнима:

- **Часы производные, а не декремент** (`F6.3`, шапка `lib/store/slices/session.ts`).
  Хранятся два абсолютных анкора — `expiresAt` (дедлайн prepaid) и `runningSince` (начало
  postpaid-спана) — и `syncClock()` **переисчисляет** число. Ровно это делает офлайн
  безопасным: сон машины, троттлинг фонового таба и просадка FPS не крадут секунды, потому
  что ответ не зависит от того, сколько раз мы спросили.
- **Один интервал на приложение** — `components/session-manager.tsx`, плюс ресинк на
  `visibilitychange` / `focus` / `online`. Второй таймер заводить нельзя.
- **Коррекция перекоса часов** — `remainingSeconds()` в `lib/time.ts` считает
  `expiresAt - serverTime` и вычитает время удержания снапшота (`markSnapshotObserved`).
  Киоск с неверными системными часами всё равно отсчитывает проданное.
- **`unreportedSeconds()`** (`lib/store/slices/session.ts`) — **готовый примитив сверки**:
  «сколько эта сессия сожгла из того, о чём сервер ещё не слышал». Уже написан в обе
  билинг-модели и уже недооценивает, а не переоценивает (комментарий там же: недоотчёт —
  безопасная сторона, переотчёт крадёт оплаченное). Новый код должен **использовать** его,
  а не заводить второй расчёт.
- **`applySnapshot()` — единственная дверь для серверной правды.** `time.added`,
  `session.paused/resumed`, ресинк на реконнекте — всё входит через неё. Сверка обязана
  входить туда же.
- **Ловушка `SESSION_LENGTH - sessionSeconds` уже поймана** (баг C1.10, документирован в
  `unreportedSeconds`): 36 минут, уничтоженных нажатием «Lock PC». Не воспроизводить.

Поэтому дальше речь **не** о переписывании часов. Речь о том, чтобы у них появилась
вторая ступень.

## 3. Ступень 2: идемпотентный отчёт по водяному знаку

Это ядро документа. Всё остальное — следствия.

### 3.1 Почему дельты не годятся

`heartbeat(elapsedSeconds)` сегодня — **дельта**: «спиши ещё 10 секунд». Дельта не
переживает ненадёжную сеть: клиент не может отличить «запрос не дошёл» от «ответ не дошёл»,
а это разные вселенные — в первой надо повторить, во второй повтор списывает дважды. В
офлайн-сценарии ретраи — норма, а не исключение, значит дельты выдадут двойное списание
на регулярной основе.

### 3.2 Решение: `(anchorId, elapsedSinceAnchor)` + max на сервере

Клиент отчитывается **не приращением, а показанием счётчика** — монотонным, всегда от
последнего серверного анкора:

```
POST /api/session/report
  { sessionId, anchorId, elapsedSinceAnchor }
→ SessionSnapshot
```

Сервер:

```
if (anchorId !== session.currentAnchorId) → игнорировать отчёт (устаревший анкор)
delta = max(0, elapsedSinceAnchor - session.acceptedSinceAnchor)
session.secondsUsed      += delta        // или debtSeconds для postpaid
session.acceptedSinceAnchor = max(session.acceptedSinceAnchor, elapsedSinceAnchor)
```

Свойства, которые из этого следуют **бесплатно**:

- **Идемпотентность.** Повтор того же показания → `delta = 0`. Ретрай безвреден.
- **Устойчивость к переупорядочиванию.** Отчёт «300», пришедший после «310», даёт `delta = 0`.
- **Самолечение после офлайна.** Потерянные отчёты не нужно восстанавливать: следующее
  показание больше, и разница списывается одним куском. Пропущенные отчёты не «теряются» —
  они догоняются.
- **Никакой очереди.** Это самое важное практическое следствие: **офлайн-очередь отчётов о
  времени состоит из одного числа**. Не список событий, не журнал, не replay-лог. Одно
  монотонное показание, которое всё равно надо будет отправить. Сравните с наивным
  «журналом операций»: он требует дедупликации, порядка и защиты от повторов — то есть
  ровно тех проблем, которых `max()` не создаёт.

`anchorId` нужен потому, что сервер переанкоривает визит (открытие, resume, `time.added`
от админа). Без него отчёт, отправленный до гранта и доехавший после, испортит новый счёт.
Новый анкор обнуляет `acceptedSinceAnchor` и делает все старые показания неприменимыми.

### 3.3 Что это меняет в существующем коде

- `heartbeat(elapsedSeconds)` → **заменяется** на `reportProgress({ anchorId, elapsedSinceAnchor })`.
  Старую дельта-подпись не оставлять даже как совместимость: один эндпоинт про время, одна
  семантика.
- `SessionSnapshot` получает `anchorId: ID` — клиент обязан вернуть его в следующем отчёте.
- `Session` получает `currentAnchorId: ID` и `acceptedSinceAnchor: Seconds`.
- `holdSeat(usedSeconds)` в `lib/seat.ts` перестаёт быть «одним отчётом в отсутствие
  heartbeat» и становится обычным вызовом того же `reportProgress` перед `pause`.
  `.catch(() => {})` там **остаётся оправданным** — но уже не опасен, потому что показание
  сохранено локально (§5) и доедет позже.
- Источник числа для отчёта — **только** `unreportedSeconds()`/производные от анкоров.
  Никакого счётчика, инкрементируемого в интервале.

## 4. Ритм отчётов

| Событие | Отчёт |
|---|---|
| каждые `REPORT_INTERVAL_MS` (10 с), пока `timerRunning` | да |
| постановка на паузу (`holdSeat`), конец визита, expiry | да, **до** смены состояния |
| `visibilitychange` / `focus` (вернулись из фона) | да |
| реконнект после офлайна | да, первым делом (§6) |
| экран блокировки, attract, отсутствие визита | **нет** |

Отчёт вешается на **тот же** интервал, что уже есть в `session-manager.tsx` (каждый 10-й
тик), а не на новый `setInterval`. Причина ровно та же, по которой в продукте один
интервал: два таймера про один визит разъезжаются на первой же спячке станции.

Отчёт **не** является запросом разрешения играть. Он ничего не блокирует и его провал
ничего не останавливает — иначе моргание сети выкидывало бы игрока из матча.

## 5. Долговременный локальный кэш (то, чего нет)

Ребут станции в офлайне сейчас теряет анкоры безвозвратно. Нужен **кэш серверной правды**,
переживающий перезагрузку.

**Что хранится** (одна запись, перезаписывается):

```ts
interface OfflineTimeCache {
  sessionId: ID
  anchorId: ID
  /** Снапшот, от которого считаем: дедлайн/начало спана + серверный штамп. */
  expiresAt: ISODateTime | null
  runningSince: ISODateTime | null
  serverTime: ISODateTime
  billingMode: BillingMode
  /** Монотонное показание, которое ещё не подтверждено сервером. */
  elapsedSinceAnchor: Seconds
  /** Последнее показание, которое сервер подтвердил. */
  acknowledgedElapsed: Seconds
  /** Монотонный источник (см. §7), для детекта подкрутки часов. */
  monotonicMark: number
  /** Локально зафиксированный конец визита, если он случился офлайн (§8). */
  localExpiry: { at: ISODateTime; elapsed: Seconds } | null
}
```

**Где:** в проде — локальное хранилище агента (`AgentBridge`, `F5`); это его естественная
роль, он и так единственный, кто переживает ребут Windows. В моке — `localStorage` как
стенд-ин, за одним фасадом `lib/offline/time-cache.ts`, чтобы подмена транспорта не
трогала логику.

**Дисциплина, без которой кэш становится дыркой:**

1. Кэш — **только кэш серверной правды плюс монотонное показание**. В нём никогда не
   лежит «сколько денег списать» и никогда — «сколько времени добавить».
2. `elapsedSinceAnchor` в кэше **только растёт**. Запись меньшего значения запрещена (это
   и есть защита от «перезагружусь и обнулю счётчик»).
3. Кэш **никогда не создаёт** визит. Нет серверного `sessionId` — нет визита; вход офлайн
   запрещён (это `C2.13`).
4. Любой ответ сервера **затирает** кэш целиком. Сервер не «мержится» с кэшем — он его
   заменяет.

## 6. Протокол сверки на реконнекте

Сверка — не отдельный алгоритм, а **первый отчёт после обрыва** плюс явное разрешение
конфликта состояний.

```
POST /api/session/reconcile
  {
    sessionId,
    anchorId,
    elapsedSinceAnchor,        // монотонное показание из кэша
    offlineSince,              // когда клиент потерял связь
    localState,                // 'active' | 'paused' | 'expired'
    localExpiry?               // если визит кончился офлайн (§8)
  }
→ {
    snapshot: SessionSnapshot,     // всегда: новая правда
    verdict: ReconcileVerdict,     // что случилось со счётом
    adjustedSeconds: Seconds       // на сколько разошлись клиент и сервер
  }
```

Порядок на клиенте (в `useReconnectResync`, `components/realtime/realtime-provider.tsx` —
там уже есть правильная развилка `if (running.current)`, сверка встаёт **перед** общим
`mutate(() => true)`):

1. Есть кэш и `timerRunning` → **сначала** `reconcile`, потом остальная ревалидация. Иначе
   SWR подтянет снапшот, ещё не знающий об офлайн-минутах, и HUD моргнёт неверным остатком.
2. Ответ адоптируется **только** через `applySnapshot()`.
3. `verdict` решает, что сказать игроку (§9). Молча расходиться нельзя.

### `ReconcileVerdict`

| Вердикт | Что произошло | Что делает клиент |
|---|---|---|
| `accepted` | сервер принял показание, счёт сошёлся | тихо продолжает |
| `adjusted` | сервер списал иначе (округление, лимит, грант в офлайне) | адоптирует, показывает объяснение с `adjustedSeconds` |
| `staleAnchor` | за время обрыва сервер переанкорил визит | адоптирует новый анкор, локальное показание **выбрасывает** |
| `closedDuringOutage` | админ закрыл/перенёс визит, пока связи не было | визит не воскрешать; экран расчёта, `releaseSeat()` |
| `expiredDuringOutage` | сервер согласен, что время кончилось | экран «время вышло», расчёт |
| `unknownSession` | сервер не знает такой сессии | кэш очистить, уйти на lock screen |

`closedDuringOutage` — тот вердикт, из-за которого сверка обязана быть отдельным
эндпоинтом, а не «просто ещё один отчёт»: клиент, вернувшийся из офлайна, может быть
**единственным**, кто ещё считает этот визит живым, и попытка досписать в закрытую строку
должна быть отбита сервером явно, а не превратиться в новый визит.

## 7. Монотонность: единственная реальная лазейка офлайна

Локальные часы производные — значит они читают `Date.now()`. Офлайн это **эксплуатируемо**:
перевод системных часов назад продлевает визит, потому что `expiresAt - now` вырастает.
Онлайн это не страшно (сервер переанкорит), офлайн — страшно.

**Правило:** прошедшее время офлайн берётся как

```
elapsed = max(wallClockDelta, monotonicDelta)
```

где `monotonicDelta` — из источника, который игрок не может подкрутить (`performance.now()`
в браузере, монотонные тики ОС в агенте). Максимум, а не монотонный источник в одиночку:
`performance.now()` не тикает во время спячки машины, а стенные часы тикают. Каждый из
двух источников слеп к своей половине, максимум видит обе — и ошибается **в сторону
клуба**, что здесь правильная сторона (недоотчёт крадёт у клуба, переотчёт крадёт у
игрока, а `max` здесь именно не даёт *украсть у клуба* обманом).

Дополнительно: обнаруженный прыжок стенных часов назад больше `CLOCK_JUMP_TOLERANCE`
пишется в кэш как флаг и уезжает в `reconcile` — сервер вправе не поверить показанию с
такой станции. Клиент **не** наказывает игрока сам: он сообщает факт, решает сервер.

## 8. Правила по билинг-моделям

Здесь ключевая асимметрия, и её надо понять до написания кода.

### Prepaid — безопасен по построению

Дедлайн `expiresAt` уже лежит локально и является **стеной, которую офлайн не может
сдвинуть**. Клиент не умеет продлевать время без сервера (покупки в офлайне запрещены,
`C2.12`), а `time.added` офлайн не приходит. Значит prepaid-визит в офлайне физически не
может переиграть проданное. **Никакой отдельный лимит офлайна prepaid не нужен** — и его
не надо изобретать.

Что происходит при исчерпании офлайн: локальные часы истекают, как и сейчас
(`syncClock` → `expireSession`). Это честно (время было продано и кончилось) и fail-safe
для клуба. Но расчёт до сервера не доехал, поэтому:

- в кэш пишется `localExpiry { at, elapsed }`;
- `releaseSeat()` выполняется локально, экран «время вышло» показывается;
- на реконнекте `reconcile` отправляет `localExpiry`, сервер закрывает строку
  (`closedBy: 'timeout'`) и отвечает `expiredDuringOutage`.

Перезагрузка страницы обойти это не может: дедлайн переживает ребут в кэше (§5), и
переисчисление снова даёт «истёк».

### Postpaid — единственный, кому нужен лимит

Walk-in накапливает **долг**, и у долга нет локальной стены: `runningSince` тикает вверх
бесконечно. Офлайн-станция может накрутить долг, который клуб никогда не санкционировал и,
возможно, не получит.

Поэтому только для postpaid вводится `OFFLINE_POSTPAID_CAP_SECONDS` (предлагаю 30 минут —
достаточно, чтобы пережить реальный обрыв, мало, чтобы стать убытком). По достижении:

- визит **не убивается** мгновенно (это walk-in с деньгами в кармане, а не читер);
- ставится на паузу с явным экраном «нужен администратор, оплата не подтверждается»;
- живой остаётся единственная кнопка — «Позвать админа» (та же, что в `C2.13`).

**Никогда** не решать это отключением локальных часов: остановленный счётчик в postpaid —
это подаренное клубом время, то есть тот же убыток, только незаметный.

## 9. Что видит игрок

Тон — тот же, что у офлайн-баннера `F4.5` и панели входа `C2.13`: **объяснено, не сломано**.
Ни одна из этих подписей не имеет права выглядеть как ошибка игрока.

1. **Часы продолжают идти.** Это главное. Офлайн-баннер уже говорит, что связи нет, и уже
   обязан не намекать на остановку клока.
2. **Метка «не подтверждено».** Пока идёт офлайн и есть неотчитанное показание, у клока в
   HUD появляется тихий маркер (`session.unverified`) с подсказкой «Клуб подтвердит это
   время, когда связь вернётся». Не тревожный цвет: это не ошибка, это статус.
3. **Расхождение объясняется.** Вердикт `adjusted` с ненулевым `adjustedSeconds` → тост с
   конкретным числом. Никогда не молча: остаток, изменившийся сам, — худшее, что можно
   сделать с игроком, который смотрел на часы весь вечер.
4. **Покупка времени офлайн запрещена** и уже сказана словами `C2.12`. Здесь ничего нового.
5. **Postpaid-кап** — отдельный экран, а не тост: он останавливает игру.

Новые ключи i18n (все три словаря `en`/`ru`/`lt`): `session.unverified`,
`session.unverifiedHint`, `session.timeAdjusted` (с плейсхолдером минут),
`session.offlineCapTitle`, `session.offlineCapBody`, `session.closedDuringOutage`.

## 10. Что этот дизайн обязан сделать невозможным

Список для ревью — каждый пункт должен быть невозможен *по построению*, а не «мы проверили»:

1. **Двойное списание при ретрае.** Невозможно: показание, не дельта, `max()` на сервере (§3.2).
2. **Потеря минут при паузе в офлайне.** Невозможно: показание в долговременном кэше, доедет
   на реконнекте (§5). Сейчас — теряется молча в `heartbeat().catch(() => {})`.
3. **Воскрешение закрытого визита.** Невозможно: `closedDuringOutage`, клиент не создаёт
   визиты (§6).
4. **Бесплатное время через ребут.** Невозможно: показание монотонно и переживает
   перезагрузку, меньшее значение записать нельзя (§5, п.2).
5. **Бесплатное время через подкрутку часов.** Невозможно: `max(wall, monotonic)` (§7).
6. **Переигрывание проданного prepaid в офлайне.** Невозможно: `expiresAt` — локальная стена (§8).
7. **Двойной счёт визита из арифметики `SESSION_LENGTH − остаток`.** Уже пойманный баг C1.10;
   отчёт строится **только** на `unreportedSeconds()`.
8. **Прерывание матча из-за сети.** Невозможно: отчёт ничего не блокирует (§4).

## 11. Дельта к контрактам

**`lib/types/session.ts`**

```ts
interface SessionSnapshot {
  // …существующее
  /** Анкор, к которому относятся expiresAt/runningSince. Возвращается в отчёте. */
  anchorId: ID
}

interface Session {
  // …существующее
  currentAnchorId: ID
  /** Наибольшее принятое показание для текущего анкора. Основа идемпотентности. */
  acceptedSinceAnchor: Seconds
}

type ReconcileVerdict =
  | 'accepted' | 'adjusted' | 'staleAnchor'
  | 'closedDuringOutage' | 'expiredDuringOutage' | 'unknownSession'

interface ReconcileResult {
  snapshot: SessionSnapshot
  verdict: ReconcileVerdict
  adjustedSeconds: Seconds
}
```

**`docs/API-CONTRACT.md` §3** — `POST /api/session/heartbeat { elapsedSeconds }` **заменяется**:

| Метод | Путь | Запрос | Ответ | Ошибки |
| --- | --- | --- | --- | --- |
| POST | `/api/session/report` | `{ anchorId, elapsedSinceAnchor }` | `SessionSnapshot` | `sessionExpired`, `conflict` (чужой анкор) |
| POST | `/api/session/reconcile` | `{ anchorId, elapsedSinceAnchor, offlineSince, localState, localExpiry? }` | `ReconcileResult` | `unauthorized` |

**`lib/mock/api/client.ts`** — оба эндпоинта **не** попадают в `OFFLINE_BLOCKED`: они и
существуют для того, чтобы отработать при плохой связи. Блокировать их — значит блокировать
собственное лечение. (`OFFLINE_BLOCKED` — про *трату* денег игроком; отчёт о прошедшем
времени тратой не является.)

## 12. Порядок внедрения (кандидаты в подпункты плана)

Строго по этому порядку — каждый шаг опирается на предыдущий:

1. **Идемпотентный отчёт.** `anchorId` + `acceptedSinceAnchor` в типах и моке,
   `heartbeat` → `reportProgress`, `holdSeat` переводится на него. Тип C (контракт).
   *Без этого шага всё остальное умножает баги.*
2. **Ритм отчётов.** 10-секундный отчёт на существующем интервале `session-manager.tsx` +
   отчёт на паузе/выходе/возврате из фона. Тип B.
3. **Долговременный кэш.** `lib/offline/time-cache.ts` за фасадом, монотонная запись,
   восстановление анкоров на старте до первого запроса. Тип C.
4. **Монотонность.** `max(wall, monotonic)` в источнике прошедшего времени + флаг прыжка
   часов. Тип C (трогает `lib/time.ts` — самое опасное место продукта, отдельным чатом).
5. **Сверка.** `POST /api/session/reconcile`, вердикты, встройка **перед** ревалидацией в
   `useReconnectResync`. Тип C.
6. **Postpaid-кап.** `OFFLINE_POSTPAID_CAP_SECONDS`, экран паузы с «Позвать админа». Тип B.
7. **UX недоверенного времени.** Маркер в HUD, тост расхождения, ключи i18n. Тип A/B.

Шаги 1–3 имеют смысл только вместе: отчёт без кэша теряется на ребуте, кэш без
идемпотентности удваивает списание. Планировать их как один блок из трёх чатов, а не как
три независимых улучшения.

## 13. Чего в этом документе НЕТ (границы)

- **Оффлайн-входа.** Нет связи — нет входа (`C2.13`). Двухступенчатый счётчик описывает
  **уже открытый** визит и ничего не говорит о том, как открыть новый без сервера.
- **Оффлайн-покупок и оффлайн-грантов.** Деньги офлайн не двигаются (`C2.12`). Ни продление
  времени, ни бар, ни выдача house-аккаунта.
- **Оффлайн-переноса сессии** между ПК (`C1.12`): решение принимает админ, значит нужен сервер.
- **Полного оффлайн-биллинга уровня desktop-ggLeap**, где агент самостоятельно открывает и
  закрывает визиты по локальному прайсу и потом сливает журнал. Это требует реального
  серверного бэкенда и нативного агента с локальной БД; в MVP-клиенте на моке этого нет и
  не планируется.
